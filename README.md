# DigitalTwinRecovery

Исследовательский стенд для второй статьи: **как безопасно восстановить уже рассогласованный цифровой двойник по аутентифицированному снимку**. Он проверяет правила допуска снимка, замену состояния вместе с метаданными и стоимость этой операции.

## Метод

`Begin` создаёт `RESYNC_REQUEST` с новым nonce. Доверенный источник под блокировкой формирует `CHECKPOINT`: состояние, его хеш, версию `(Epoch, Sequence)` и nonce запроса. Полный режим проверяет тип, HMAC, текущий сеанс, срок действия, версию и хеш фактического содержимого. Контекст запроса закрывается перед установкой; повторный ответ закрытого сеанса не применяется.

Снимок допускается, если его версия не ниже `MinimumVersion`: максимума установленной версии и версии, уже достоверно известной из активной проверки. `ObserveKnownVersion` и аргумент `Begin(knownVersion)` принимают **доверенное знание**, а не произвольное сообщение из сети. Эта граница явная: интеграция с проверкой актуальности из первого проекта пока не является отдельным сетевым сервисом.

Равная версия допускается для ремонта повреждённого состояния. Более новая Epoch допускает маленький Sequence; старая Epoch отклоняется. Повышение известной версии выше локальной переводит готовый агент в `NeedsRecovery`. Пока ожидается снимок или база требует восстановления, дельты блокируются. После установки разрешены последовательные обновления от установленной базы. Снимок соответствует версии в момент захвата; источник может продолжить изменяться до доставки. Повторная проверка и возобновление потока нужны для дальнейшей актуальности.

Состояния: `Ready`, `AwaitingSnapshot`, `NeedsRecovery`, `CommunicationLoss`, `InstallationFailed`. Три сравниваемых режима: `HmacOnly`, `HmacVersion` (только локальная граница версии), `Full` (известная граница, сеанс и хеш). Ослабленные режимы специально показывают, чего недостаточно в отдельных проверках.

## Замена и сбои

Состояние, версия, хеш и минимальная известная версия составляют один неизменяемый `LocalRecord`. В памяти меняется одна ссылка. Файловый вариант пишет весь кортеж в временный файл в том же каталоге, вызывает `Flush(true)`, заменяет целевой файл и публикует новую ссылку. Внешняя SHA-256 оболочка выявляет повреждение записи; она не защищает от злонамеренного отката диска.

Самопроверка реально завершает дочерний процесс в четырёх точках: перед записью, посередине записи, после Flush до замены, после замены до публикации ссылки. После запуска читается целиком старый или новый кортеж. Незавершённый временный файл не становится актуальной записью. Отдельно проверяются сохранение границы версии при повторном открытии, возобновление дельт, новая Epoch и чтение целого кортежа конкурентными читателями. Пример раздельной записи состояния и версии — логический контрпример смешанного кортежа, не результат испытания сбоя такого хранилища.

## Эксперимент и метрики

12 сценариев × 3 режима: правильный снимок, ремонт той же версии, подмена, другой сеанс, откат, снимок ниже известной версии, новая и старая Epoch, закрытый запрос, истёкший срок, неверный хеш доверенного производителя и дельта во время восстановления. Последний сценарий проверяет установку именно захваченной версии, а не совпадение с постоянно меняющимся источником. Диагностика неверного хеша источника не выдаётся за возможность атакующего подделать HMAC.

`Runs` — число повторений каждой ячейки: 10 000 дают 360 000 функциональных случаев. Счётчики: допущенные/отклонённые ответы, сохранение состояния при отказе, точное соответствие принятому снимку, приём ниже известной границы и приём из другого сеанса. `correct_after_accepted` означает правильную установку содержимого снимка; само по себе оно не доказывает свежесть. Для этого нужны два последних счётчика и политика версий.

Отдельный benchmark выполняет реальные локальные операции для двоичных состояний размером 17, 4 113, 65 553 и 1 048 593 байта. Для каждого размера сравниваются Memory и File: 3 прогрева, затем по умолчанию 30 измерений. Независимо измеряются создание снимка источником и проверка с установкой получателем, используя Stopwatch. Время сети и передачи исключено. Размер обозначает двоичное состояние, а не размер всего пакета или JSON-файла. Проверка с файловой установкой включает сериализацию файловой оболочки, checksum, Flush и замену.

JSON содержит среднюю, медиану, P95, максимум; CSV сводки — среднюю и P95, а `samples.csv` хранит все 240 первичных замеров. Числа зависят от машины, сборки, GC и файловой системы. Seed воспроизводит функциональные входы; он не фиксирует времена benchmark. Для сравнительных выводов нужно повторить замеры на целевом стенде и указать конфигурацию.

## Границы

Файловое хранилище рассчитано на одного писателя. Проверены сбои процесса на локальной Linux-файловой системе. Отключение питания, надёжность других файловых систем, несколько писателей, злонамеренный откат диска и долговременное хранение Epoch источником не проверены. Flush и замена без подтверждённой стратегии синхронизации каталога не дают здесь заявленной гарантии при отключении питания.

Обнаружение рассогласования — предпосылка этого проекта. Автоматический интегрированный контур из двух проектов, транспорт, фоновые дельты во время передачи, очереди возобновления и ключевое хозяйство остаются за пределами данной серии. Снимок подтверждает захваченную версию, не вечное равенство источнику.

## Запуск

Нужен .NET 8 SDK. Сторонних NuGet-пакетов нет.

```bash
dotnet build -c Release
dotnet run --no-build -c Release -- --self-test
dotnet run --no-build -c Release -- --run --runs 10000 --seed 20260809 --output results.local
```

Или `RUNS=10000 bash scripts/reproduce.sh`. В Windows используйте команды `dotnet` выше. Без `--run` запускается локальный веб-интерфейс; адрес указан ниже. Он показывает таблицы и позволяет скачать JSON. API: `GET /health`, `GET /api/defaults`, `POST /api/experiment` с параметрами JSON. CLI принимает `--runs`, `--seed`, `--output`; остальные настройки доступны через API.

В `results.local` записываются `report.json`, `functional.csv`, `samples.csv`, `summary.csv`. Проверка сводок по первичным данным: `python3 scripts/check_results.py results/reference` (Python 3, без сторонних пакетов). Можно указать `results.local` для нового прогона.

В JSON есть параметры, ограничения, среда исполнения и SHA-256 сборки. `results/reference` содержит реально выполненный прогон с 10 000 повторениями, seed 20260809, и описание проверки. У сводного reference JSON удалён большой массив samples: первичные данные сохранены отдельным CSV. Временные метки окружения не участвуют в эксперименте.

Архивная reference-серия получена прямой компиляцией Roslyn из SDK 8.0.414 с предупреждениями как ошибками и запуском под .NET 8.0.20. Обычная SDK-сборка Release, самопроверки, короткий эксперимент и пересчёт архивных и новых сводок дополнительно проверены на Windows 11 с SDK 10.0.102 и runtime .NET 8.0.7. Подробности — в [отчёте проверки](results/validation/windows-2026-10-10.md). В репозитории предусмотрен GitHub Actions для сборки, самопроверки и короткого прогона.

## Происхождение и структура

Проект производный от [DigitalTwinSync](https://github.com/e-shchukin/DigitalTwinSync), коммит `763aae5ee00912d2c4c484dfc3d931b2cfbfcb3c`. Git-история сохранена; подробности в [UPSTREAM.md](UPSTREAM.md). Старые результаты не перенесены как результаты нового протокола.

`Core.cs` содержит общее неизменяемое состояние, версии, однозначную сериализацию, HMAC-SHA256, SHA-256, доверенный источник и часы. Тип сообщения включён в MAC и отдельно проверяется получателем: отражённый запрос не становится ответом. Детерминированные ключи и nonce используются только в воспроизводимых сценариях; обычные агенты используют криптографический генератор nonce. Это исследовательский стенд; в нём нет управления секретами, транспорта к физическому объекту и защиты файлов от администратора.

`SelfTests.cs` проверяет свойства протокола. `Program.cs` даёт CLI и локальный HTTP API, `Export.cs` — CSV. Обе статьи пока не изменены: выводы следует привязать к конкретному новому протоколу и сохранённым сериям.

Локальный интерфейс: http://localhost:5082 после `dotnet run`.
